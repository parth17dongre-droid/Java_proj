---------------------------------------------------------------------
1. PROJECT OVERVIEW
---------------------------------------------------------------------
- EV charging slot booking system ("EV.Bolts"): EV owners register vehicles,
  find/book charger slots, pay from a wallet; admins manage chargers/slots/revenue.
- Semester-3 Java + DBMS mini project; 3 tiers: React SPA -> Spring Boot REST API -> MySQL.
- Problem statement: no double booking, pay-before-unlock, bill on actual energy used,
  fast vs slow charger pricing, maintenance handling.
- Roles: USER (EV owner), ADMIN (station operator). [CHECK which are implemented]
- Core modules: Auth, Vehicles, Chargers/Slots, Bookings, Billing, Wallet, Reports.
- Mention what is done vs planned honestly (git log shows phases).

---------------------------------------------------------------------
2. ARCHITECTURE
---------------------------------------------------------------------
- Layered backend: Controller -> Service -> Repository -> Entity (DB).
  Controllers: HTTP only. Services: business rules + @Transactional. Repos: Spring Data JPA.
- DTO layer (dto/): request/response objects so entities (e.g. password hash) never reach JSON.
- Packages: config, controller, dto, model (entities), repository, service, utils.
- Stateless REST API: no server session; identity travels in a JWT cookie.
- Frontend talks only to /api/**; Vite dev proxy forwards /api -> localhost:8081 (no CORS pain in dev).
- Dependency injection via constructor injection (Spring IoC container, beans).
- Separation of concerns, single responsibility, thin controllers.
- Diagram idea: Browser -> Vite/React -> HTTP+Cookie -> Security filter chain -> Controller
  -> Service -> JPA/Hibernate -> JDBC -> MySQL.

5. SECURITY / AUTHENTICATION (high-value slide)
---------------------------------------------------------------------
- Password hashing: BCrypt (salted, adaptive cost) — only hash stored.
- JWT (jjwt): HMAC-signed; subject = username; extra claims (user id, token type).
- Two tokens: short-lived access token (minutes) + long-lived refresh token (days),
  refresh token stored in DB (users.refresh_token) so it can be revoked on logout.
- Access token in HttpOnly cookie -> JS can't read it (XSS-resistant); SameSite/Secure flags
  for production [CHECK].
- Custom JwtFilter (OncePerRequestFilter) placed before UsernamePasswordAuthenticationFilter:
  parse cookie -> validate -> populate SecurityContext (Authentication.getName() = username).
- SecurityFilterChain: CSRF disabled (stateless + JWT), STATELESS sessions,
  /api/auth/** public, everything else authenticated.
- CORS: allowed origin = frontend only, credentials allowed.
- Frontend flow: apiFetch -> on 401 call /refresh -> retry once -> else redirect to login.
- ProtectedRoute component guards pages client-side (server is still the real gate).
- Authorization per user: services scope data by authenticated username (users only see own vehicles).
- Input validation at trust boundary (DTO validation) + DB CHECK constraints = defence in depth.
- Talking point: a real bug found — JWT subject was username but service looked up by email.

7. DBMS — SCHEMA DESIGN (main focus; source: database/schema.sql)
---------------------------------------------------------------------
Database: ev_charging, utf8mb4, InnoDB. Tables (add/remove as schema changes) [CHECK]:
- users            — identity (EV owners + admins), unique login, hashed password
- wallets          — 1:1 with user (UNIQUE user_id), balance, version
- vehicles         — N:1 user; make/model/year/battery_capacity_kwh/max_charging_power_kw
- vehicle_connectors — vehicle's supported plug types (multi-valued attribute table)
- chargers         — physical points: type FAST/SLOW, power_kw, rate_per_kwh, status
- slots            — bookable time windows per charger, status AVAILABLE/BOOKED/IN_PROGRESS
- bookings         — user reserves a slot, lifecycle BOOKED->IN_PROGRESS->COMPLETED / CANCELLED
- bills            — 1:1 with booking; advance_amount, energy_kwh, final amount, payment_status
- wallet_transactions — append-only ledger: TOPUP, ADVANCE_DEBIT, FINAL_DEBIT, REFUND
- Views: v_available_slots, v_slot_board, v_daily/weekly/monthly_revenue, v_revenue_by_charger_type
- Draw an ER diagram: users 1-1 wallets; users 1-N vehicles; vehicles 1-N connectors;
  chargers 1-N slots; users 1-N bookings; slots 1-N bookings (history) but 1 live;
  bookings 1-1 bills; wallets 1-N wallet_transactions; bills 1-N wallet_transactions.

Relationship types to name explicitly
- 1:1 (users-wallets, bookings-bills) enforced with UNIQUE on the FK.
- 1:N (users-vehicles, chargers-slots) via FK on the "many" side.
- Multi-valued attribute -> separate table (vehicle_connectors, composite PK).
- Optional relationship: wallet_transactions.bill_id NULL for top-ups.

8. DBMS — CONSTRAINTS & INTEGRITY
---------------------------------------------------------------------
- Entity integrity: PRIMARY KEY on every table, BIGINT AUTO_INCREMENT surrogate keys.
- Referential integrity: FOREIGN KEYs; ON DELETE CASCADE for dependent rows (vehicle_connectors).
- Domain integrity: CHECK constraints (balance >= 0, end_time > start_time, rate > 0,
  status IN (...), year BETWEEN 2010 AND 2030, connector_type IN enum list).
- UNIQUE constraints: user email/username, charger_code, (charger_id, start_time) for slots.
- NOT NULL / DEFAULT / ON UPDATE CURRENT_TIMESTAMP audit columns.
- Conditional CHECKs (business rules in DB): SETTLED bill must have energy+amount+settled_at;
  TOPUP has no bill, every other txn type must have one.
- Composite primary key (vehicle_id, connector_type) prevents duplicate rows.
- Why DB-level rules: still protect data if Java code has a bug or another client writes.
- Enum strategy: VARCHAR + CHECK (portable, matches @Enumerated(STRING)).
- Money as DECIMAL(10,2), energy DECIMAL(8,3), never FLOAT; vehicle kWh as DOUBLE (non-monetary).

---------------------------------------------------------------------
9. DBMS — NORMALIZATION
---------------------------------------------------------------------
- 1NF: atomic values — multi-valued connector list split into vehicle_connectors.
- 2NF: no partial dependency — composite-key table has no extra non-key columns.
- 3NF: no transitive dependency — charger details live in chargers, not repeated in slots/bookings.
- Deliberate denormalisation: bills.rate_per_kwh copied from chargers at booking time
  so later price changes never rewrite old bills (historical accuracy).
- balance_after in ledger = snapshot (audit/statement speed) — justified redundancy.

10. DBMS — CONCURRENCY, TRANSACTIONS, ACID (high-value slide)
---------------------------------------------------------------------
- ACID with InnoDB; Spring @Transactional wraps multi-step operations
  (e.g. book slot + create bill + debit wallet + write ledger = one unit; all or nothing).
- Double-booking prevention, three layers:
  1) JPA optimistic locking: @Version column on slots/wallets.
  2) Generated column active_slot_id (VIRTUAL) = slot_id only while booking is live,
     + UNIQUE index -> DB itself rejects 2nd live booking; NULLs for history don't clash.
  3) Transaction isolation (InnoDB default REPEATABLE READ); pessimistic lock
     (SELECT ... FOR UPDATE) as an option.
- Wallet: version column + CHECK(balance >= 0) -> no negative balance even on race.
- Optimistic vs pessimistic locking comparison; lost-update problem explained.
- Append-only ledger = auditable money trail; balance can be re-derived.
- Mention isolation levels & anomalies: dirty read, non-repeatable read, phantom read.

12. ORM — JPA / HIBERNATE MAPPING
---------------------------------------------------------------------
- @Entity/@Table/@Id/@GeneratedValue(IDENTITY) <-> AUTO_INCREMENT.
- camelCase field -> snake_case column (Spring naming strategy): batteryCapacityKwh -> battery_capacity_kwh.
- @ManyToOne(fetch = LAZY) owner -> vehicles.user_id; why LAZY (avoid N+1 / unneeded loads).
- @ElementCollection + @CollectionTable -> vehicle_connectors; @Enumerated(STRING).
- @Column(nullable, unique, length, updatable=false), @PrePersist for timestamps.
- ddl-auto=update (dev convenience) vs hand-written schema.sql (source of truth for production);
  note: keep entities and schema.sql in sync [CHECK mismatch with users table].
- Views mapped via @Entity + @Immutable or native queries.
- N+1 problem, EAGER vs LAZY, derived queries vs @Query/JPQL vs native SQL.
- Repository: JpaRepository gives CRUD, paging, sorting for free.

13. BUSINESS LOGIC FLOW (walk-through slide)
---------------------------------------------------------------------
1. Sign up -> BCrypt hash saved -> JWT cookies issued.
2. Register vehicle (make, model, year, battery kWh, connectors) -> validated -> saved for that user.
3. Browse available slots (v_available_slots hides maintenance chargers and past/booked slots).
4. Book slot -> booking BOOKED + bill PENDING (transaction).
5. Pay advance (power x hours x rate) from wallet -> bill PAID -> charger unlocks.
6. Charging ends -> actual energy -> final amount = energy x rate -> bill SETTLED;
   difference charged (FINAL_DEBIT) or refunded (REFUND).
7. Cancel -> booking CANCELLED, active_slot_id becomes NULL so slot can be rebooked.
8. Admin: manage chargers/slots, set maintenance, view revenue views.
